# CLAUDE.md — englishgate-site standing rules (every session, no exceptions)
1. SCOPE LOCK: Build ONLY what the current prompt specifies. Never add sections, features, or copy on your own initiative — the "Need someone to talk to" card is the precedent that forbids this. If you believe something is missing, propose it in one line at the end of your report; do not implement it.
2. NO INVENTED FACTS: Never write factual claims about the academy (ages, prices, counts, services, policies) not sourced from strings.js/staff.js or explicitly provided in the prompt. Honest placeholder beats invented specific.
3. DEPLOY GATE: Never deploy or release a hold without an explicit approval in the CURRENT session that names the sprint ("S12 approved — deploy"). Approvals never batch, never carry across sprints.
4. LANGUAGE PURITY: EN mode pure English, AR mode pure Arabic (wordmark + toggle exempt). Scanner must pass before any "done" claim.
5. VERIFICATION: full matrix (webkit/chromium/firefox × mobile/desktop × EN/AR) before "done". No emojis anywhere — SVG icons only.
6. NETLIFY MIRROR: Netlify deploys use token auth from ~/.zshrc sourced in the same shell (`source ~/.zshrc && npx netlify-cli deploy --prod --dir=dist` — NETLIFY_AUTH_TOKEN + NETLIFY_SITE_ID load from the rc file); never suggest `netlify-cli login` (interactive OAuth breaks on this machine). After deploying, confirm the mirror's bundle hash matches production.
7. OWNER'S VERIFIER: `qa/verify-points.mjs` is the owner's INDEPENDENT production verifier, deliberately separate from Claude's QA. Claude must NEVER delete, rewrite, or "improve" it. The owner runs it personally after every deploy (`node qa/verify-points.mjs` from the repo root, optional site URL as the argument). If a legitimate change makes one of its checks fail, report the conflict and stop — the owner updates the file, not Claude.
8. DEPLOY GATE — THE PRODUCTION ROUTING GATE (S49, same standing as Rule Zero): **a deploy is not done until `qa/post-deploy-gate.mjs` passes against production.** It is wired into `npm run deploy` and runs AFTER the upload; if it fails, the deploy failed — fix production or roll back. It is the owner's verifier for ROUTING, exactly as `verify-points.mjs` is for content: **a builder never edits, weakens, skips or `|| true`s it to make a deploy pass.** If a legitimate change makes it fail, report the conflict and stop — the owner updates the gate, not Claude. It exists because the whole local bar runs against `vite preview`, whose SPA fallback is Vite's, while production is served by Cloudflare Pages' `_redirects` — so a Pages-only routing regression is structurally invisible before deploy. One such regression (a stray `404.html`, a Pages magic filename that outranks the SPA catch-all) took 13 of 14 routes to 404 in production while every local check stayed green.
